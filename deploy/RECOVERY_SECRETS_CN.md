# TermRelay 灾难恢复密钥保管清单

数据库备份只能恢复业务数据，**不能替代生产环境密钥备份**。如果原服务器彻底失去访问，而关键密钥只存在原服务器 `.env` 中，即使 PostgreSQL 可以恢复，登录、2FA、OAuth、支付或其他外部集成仍可能失效。

## 必须独立保管的核心项目

至少把以下值保存在生产服务器之外、由项目授权人员控制的安全位置：

- `POSTGRES_USER`
- `POSTGRES_PASSWORD`
- `POSTGRES_DB`
- `JWT_SECRET`
- `TOTP_ENCRYPTION_KEY`
- 管理员账号恢复所需信息
- 生产环境实际使用的 OAuth client secret
- 生产环境实际使用的支付/回调密钥
- 生产环境实际使用的第三方 API secret
- 如使用 Cloudflare Tunnel：对应的 Tunnel 配置/恢复权限
- PostgreSQL 备份使用的 `age` **私钥**

具体启用了哪些额外密钥，以当前生产 `.env` 和业务配置为准。

## 特别说明

### JWT_SECRET

必须固定并独立保存。丢失后重新生成会使已有登录会话失效。

### TOTP_ENCRYPTION_KEY

必须固定并独立保存。丢失后可能导致数据库中已有 TOTP/2FA 数据无法正常使用。

### PostgreSQL 密码

新服务器恢复时可以选择继续使用原密码，也可以在计划迁移中更换。但恢复流程必须明确知道目标 PostgreSQL 的有效凭据。

### age 私钥

生产服务器只需要用于加密的公开 recipient；用于解密数据库备份的私钥应优先留在独立恢复设备/安全存储中，而不是长期放在生产服务器。

## 不要这样保管

不要把真实密钥：

- 提交到公开 GitHub；
- 写入 `docker-compose.yml`；
- 发到公开聊天/Issue；
- 和数据库备份一起长期只保存在同一台生产服务器；
- 只保存在合作方个人控制、你完全无法恢复的单一账号中。

## 推荐保管形式

最简单的做法是维护一份**加密的生产恢复包**，至少包含：

1. 当前生产 `.env` 的加密副本；
2. PostgreSQL 备份解密私钥；
3. 当前正式 `TERMRELAY_IMAGE_REF` 或 digest；
4. 域名/DNS/Cloudflare 恢复说明；
5. 最近一次成功恢复演练的日期。

恢复包应至少有一份位于生产服务器之外。

> 这份文件只记录“需要保管什么”，仓库中永远不要填写真实 secret。
